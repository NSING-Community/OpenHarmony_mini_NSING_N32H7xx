## 2. 术语与边界：先把"是什么"说准

> 这一节是专门为"FAE 答客户"和"开源读者不跑偏"准备的。**术语错一次，后面全错。**

### 2.1 准确的层次关系 ▣

```
OpenHarmony（开源项目）
└── MINI 系统（面向小内存设备的"最小系统"裁剪集，组件化拼装）
    ├── 内核层        kernel/liteos_m            ← 只是"内核"，不是整个系统
    ├── 驱动框架层    drivers/hdf_core           ← HDF：框架 + 适配层 + 平台驱动
    ├── 系统服务层    foundation/systemabilitymgr (samgr_lite)
    │                 base/startup (bootstrap_lite / init)
    │                 base/hiviewdfx (hilog_lite / hievent_lite)
    ├── 基础库        third_party: musl / cmsis / bounds_checking_function / unity
    ├── 构建系统      hb + gn + ninja + 组件化(bundle.json) + 产品配置(vendor/config.json)
    ├── 测试框架      test/xts (hctest / acts)
    └── 芯片与板级适配 device/soc/…（SoC 事实）+ device/board/…（板级事实）
```

**本工程实测的组件清单**（源：`vendor/Nsing/n32h7xx_eval/config.json` 的 `subsystems`）▣

|---|---|
| applications | `n32h7xx_sample_app` |

| hdf | `hdf_core`, `drivers_tools` |

> 而不是"一个内核"。后面每一节都回到这张表上指出"我们刚讲的是哪一行"。

### 2.2 常见错误说法对照表（FAE 最需要）▣

| ✗ 错误说法 | ✓ 准确说法 | 为什么重要 |
|---|---|---|
| "OpenHarmony 就是 LiteOS-M" | 鸿蒙是**系统**，LiteOS-M 只是它可选的一个**内核**（另有 LiteOS-A、UniProton） | 客户问"你们支持鸿蒙吗"，问的是系统，不是内核 |
| "HDF 是内核的一部分" | HDF 是**驱动框架**，运行在内核之上，用内核的任务/内存/IPC；在 mini 上走 `drivers/hdf_core/adapter/khdf/liteos_m` | 决定"HDF 出问题要不要改内核" |
| "驱动就是写寄存器" | HDF 下分**框架层/适配层/芯片驱动**三段，芯片驱动还要再分 **SoC 薄封装 + HDF 驱动** | 决定改动的归属与可维护性 |
| "hcs 是配置文件，读不到就改代码" | hcs 会**编译成数据链进镜像**，运行时由 HDF 解析成设备树；读不到通常**是两段式没写对** | 这是最高频的"配了不生效" |
| "应用直接调驱动函数" | 应用只调**平台 API**（`GpioWrite`/`UartWrite`/`I2cTransfer`），经服务/控制器找到驱动 | 决定能不能换芯片不改应用 |

### 2.3 为什么要以 SDK 1.3.0 为基础，而不是以裸机为基础 △

- SDK 给的是**寄存器级事实**（时钟树、引脚 AF、时序参数、外设例程）；系统给的是**框架与运行环境**。
- 本工程的边界：**SDK 只被 SoC 薄封装文件引用**，HDF 驱动与应用层一律不引 SDK 头文件。
- 后果（这是全课最重要的一条设计约束）：
  - 换 SDK 版本时，只有薄封装要动；
  - HDF 驱动可整份复用到别的 SoC（只换薄封装）。
  - 反面：驱动直接引 SDK 头，会撞 `enum IRQn` 重定义（见 §6 H8）。

### M2　启动链：最小可运行系统（16 min，▣ 含演示①）

- 目标：能按顺序说清"从复位到应用跑起来"的 8 步，并知道每步的验证方法。
- 启动链（**本节骨架，建议直接做成 PPT 图**）：

| 步 | 做什么 | 代码位置 | 失败了长什么样 |
|---|---|---|---|
| 1 | `Reset_Handler` → `SystemInit` | SoC `startup_n32h78x_cm7_gcc.s` | 完全没反应 |
| 2 | 时钟 Mode0 + **释放 CM4** | `BoardClockInit()` | 零串口输出（总线 stall，等 PLL LOCK 自旋不退出） |
| 3 | 早期 LED | `BoardLedEarlyOn()` | 用来证明 main 活着（不依赖调度） |
| 4 | 串口 | `UartInit()`，等 **`TXDE`** 不是 `TXC` | 输出乱码/无输出 |
| 5 | 内核 | `LOS_KernelInit()`：堆、定时器池、中断向量表 | `OsSwtmrInit error` |
| 6 | HDF | `DeviceManagerStart()`：解析 hcs → 建 host/device → 跑 Bind/Init | 驱动不出现、或出现了又消失 |
| 7 | 引导层 | `OHOS_SystemInit()`：六层 initcall | `SYS_RUN` 应用不被拉起 |
| 8 | 调度 | `LOS_Start()` | 卡死/心跳不动 |

- 四个必讲的技术点：
  1. **堆**：`board.ld` `_Min_Heap_Size = 0x17000`（92KB），实测 `__heap_start=0x24004DE0` / `__heap_end=0x2401BDE0`
     → 差 0x17000 正好对上；堆是 NOLOAD，**改堆不会改变镜像大小**，必须用 `nm` 验证
  2. **向量表对齐**：`LOSCFG_ARCH_HWI_VECTOR_ALIGN = 0x800`（432 条向量 → 需 2048 字节对齐），
     `VECTOR_ALIGN ≥ 向上取 2 的幂(向量数 × 4)`
  3. **FPU 的 C/ASM 一致性**：GCC 汇编器**不会**自动定义 `__FPU_PRESENT/__FPU_USED`，
     只在 C 侧经 `core_cm7.h` 定义 → 上下文布局差 0x40 → 崩在 `Swt_Task`，`PC=0xAA00001E`、`R7=0x04040404`
  4. **`-nostdlib` 下不能用 musl printf**：会挂死；本工程自实现格式化器，镜像从 42824 → 29664 B
- 演示①挂点与观察点见 §4。
- ○ 可挑讲：双核释放（`RCC_EnableCM4`）为什么会导致"零输出"
- △ 文档详写：`target_config.h` / Kconfig / `board.ld` 三处分别管什么

### M4　HDF I2C 全链路与地址案例（16 min，▣ 含演示②）

- 目标：用一个完整驱动，把 §6 的抽象概念落到"每一行代码"。
- 要点：
  1. 四个文件的分工（**这就是新增任何平台驱动的模板**）：

     | 文件 | 职责 | 能不能引 SDK 头 |
     |---|---|---|
     | `n32_i2c_hw.h` | 薄封装接口（只有原型 + 常量） | ✗ 不能 |
     | `n32_i2c_hw.c` | 寄存器级实现（引 SDK 头） | ✓ 可以 |
     | `i2c_n32h7xx.c` | HDF 驱动：hcs 读取、cntlr 注册、transfer 实现 | ✗ 不能 |
     | `hdf_config/…/i2c_config.hcs` | 参数（port / speed） | — |

  2. 接线三要素缺一不可：Kconfig `LOSCFG_DRIVERS_HDF_PLATFORM_I2C=y` + `BUILD.gn` 厂商分支 + hcs 节点（**manager + controller 两个**）
  3. **"7 位 vs 8 位地址"案例**（本课最新、最典型）：
     - 现象：地址阶段 NACK（`NAKF=1`、`BUSY` 卡住、`WRAVL` 永不来），换时钟/时序/上拉全无效
     - 根因：`I2C_ConfigSendAddress()` 把地址**原值写进 SADR，不左移**（`n32h7xx_i2c.c:310`），
       所以必须传 8 位总线字节 `0xA0`；我们传了 7 位 `0x50` → 线上实际是 7 位地址 `0x28` → 无器件
     - 修复：在薄封装里 `#define N32_I2C_ADDR_BYTE(addr7) ((uint32_t)(addr7) << 1)`，**5 处调用统一走它**
     - 旁证：HDF 的 `I2cMsg.addr` 是 7 位 —— 官方参考驱动 `i2c_stm32f4xx.c:345` 自己写 `(devAddr << 1)`
     - 反汇编验证：`objdump -d` 里能看到 `movs r1, #160 ; 0xa0` 与 `mov.w r1, r8, lsl #1`
  4. 怎么证明"真的走了 HDF"（三层证据，见 §6 H7）
- 演示②挂点见 §4。
- ○ 可挑讲：I2C 的中断/DMA 模式与本节轮询实现的差别

### M5　XTS 与认证（12 min，▣ 含演示③）

- 目标：听懂"认证在验什么"，会读 XTS 日志，知道失败怎么归因。
- 要点：
  1. XTS 不是独立工程：`config.json` 里加 `xts: acts` 组件，编译时开 `build_xts=true` 且用 debug 配置
  2. hctest 机制（**关键，很多误解都在这**）：
     ```c
     /* test/xts/tools/lite/hctest/src/hctest_service.c:118 */
     case MSG_START_TEST:
         if ((testService->flag & TEST_FLAG) != TEST_FLAG) {
     #ifdef HCTEST_NEW_RUNNER
             RunAllXtsTests();
     #else
             INIT_TEST_CALL();      /* ← 套件由 hctest 自己遍历执行 */
     #endif
     ```
     → 套件通过 `RUN_TEST_SUITE` 注册进 `test` 层 initcall，**由 hctest 服务在调度器启动后执行**
  3. 案例：**套件跑了两遍** —— `main()` 里也遍历了一次 `__zinitcall_test_*`，与 hctest 的 `INIT_TEST_CALL()` 重复
     → 删除 `main()` 里的遍历（`main()` 只打印"注册了多少 suite entry"）
  4. 结果判读：用例数 / 通过 / 失败；本工程实测 **157 用例 / 0 失败**
  5. 认证参数（`FirstApiVersion`、`AbiList`、`BuildRootHash` 等 8 处）：先说"要改"和"取值从哪查证"，细节留文档 △
- 演示③挂点见 §4。
- △ 文档详写：认证流程 6 步、六个套件的适配性总表、分批烧录策略

### M6　调试方法论精华（12 min，▣）

> 这节不讲"某个 bug 怎么修"，讲"没见过的问题怎么想"。

- **A. 故障指纹表**（先分类，再查因）▣

| 指纹 | 指向 |
|---|---|
| `Type=9 UsageFault` + 寄存器含 `0xAA0000xx` / `0x04040404` | 上下文错位（栈/FPU 布局不一致） |
| `Type=11 ImpreciseBusFault` + `FaultAddr=0xABABABAB` | PC 不可信 → 改查"内核改了哪个全局状态" |
| 总线错误 + 寄存器全 0 / 明显不合理 | 寄存器没写进去 → 查外设时钟/复位 |
| "内核前正常、内核后必崩" | 常是 `HalHwiInit()` 打开了错误上报，把旧问题暴露出来 |

- **B. 三板斧** ▣：早期 LED（不依赖调度）→ 逐字符输出（不走 printf）→ 单一变量隔离探针；**每次只改一处再烧**
- **C. 证据纪律** ▣（FAE 最容易犯的几条）
  1. 判成功一律 `!= 0` 或 `== SUCCESS`，**绝不写 `== 0`**（`ErrorStatus{ERROR=0, SUCCESS=1}`）
  2. "配置失败"先打印**原始返回值**，别只看自己的布尔判断
  3. 判"有没有重编"看 **`.o` 数量 + ELF 时间戳**，别信工具报的耗时（本工程复现过：删净 523 个 `.o` 仍报 5 秒）
  4. 改完必须 `objdump`/`nm`/`strings` 验证生成码，别只看"编译通过"
- **D. 与能跑的官方裸机逐项对比法** △：startup / ld MEMORY / 复位向量 / main 反汇编 / bin-hex LMA / 向量表 / SysTick
- **E. 三个思维陷阱**（各 2 分钟，口述即可）○
  1. **盯错标志**：一直等 `WRAVL`（成功标志），故障时置位的却是 `NAKF`（错误标志）→ 错误码把人骗到"数据阶段"方向
  2. **照抄 demo 只抄了形**：引脚/时钟/时序/状态机全抄，却把 `0xA0` 自己"翻译"成 `0x50`
  3. **诊断工具本身是错的**：自以为能二分的对照实验，因为同样传错地址，必然给出同样的假结论

## 6. HDF 专章（M3 展开，34 min）

> 目标定得很具体：**听完能照着写出第 3、4 个平台驱动**。
> 源码只精读 3 处（H5 的 `.hdf.driver` 段、H6 的虚表、H3.3 的 `property` 反查），其余讲结构与用法。

### H1　为什么需要 HDF（3 min）▣

- 问题域：同一颗芯片要给多个产品用、同一个产品要换多颗芯片 → 驱动与业务必须解耦
- HDF 给的三个能力：**统一驱动模型**（Bind/Init/Release）、**配置与代码分离**（hcs）、**按名字找服务**（不写死地址）
- 对照裸机：裸机是 `main()` 里 `I2C_Init(); while(1){...}`；HDF 是"配置在 hcs、代码在驱动、业务在应用"

### H2　三层架构与目录（3 min）▣

```
drivers/hdf_core/
├── framework/        框架本体（设备管理、hcs 解析、服务发布、平台 API 实现）
├── interfaces/       对外头文件（gpio_if.h / uart_if.h / i2c_if.h …）
└── adapter/
    ├── khdf/         内核态 HDF 适配（我们用的：khdf/liteos_m）
    ├── platform/     各外设的平台驱动（gpio/ uart/ i2c/ spi/ pwm/ …）← 我们写的地方
    ├── uhdf/ uhdf2/  用户态 HDF（mini 不用）
    └── build/ hdf_adapter.gni
```

- 讲法：把这三层和"谁能改/谁不能改"绑起来说——`framework` 别动，`adapter/platform` 里加厂商分支。

### H3　hcs 设备树（8 min）▣ 本节最容易被讲漏

**H3.1 字段语义（逐字段讲，给一张表）**

| 字段 | 含义 | 我们踩过的坑 |
|---|---|---|
| `moduleName` | 与 `HdfDriverEntry.moduleName` **字符串相等**才匹配 | 不一致 → 驱动根本不启动，且无任何报错 |
| `policy` | 0 = 不发布 service；2 = 发布（需 `serviceName`） | `policy=2` 但 service 未创建 → **节点被析构，设备"消失且无日志"** |
| `preload` | 是否预加载 | 目前用 0 |
| `priority` | 加载顺序（小者先） | I2C manager 必须早于 controller |
| `permission` | service 权限 | — |
| `deviceMatchAttr` | **指向参数节点的 match_attr** | 留空 → 参数全被忽略（见 H3.3） |
| `serviceName` | 发布出去的 service 名 | `policy=0` 时必须为空 |

**H3.2 编译链路（必须讲清，否则"hcs 改了没生效"永远说不明白）**

```
hdf.hcs ──(hc-gen)──▶ hdf.hcb ──▶ 编进镜像（随 .rodata，无独立 .hcs 段）──▶ DeviceManagerStart() 解析成树
   ↑ #include 各区域文件        路径示例：out/…/gen/vendor/Nsing/n32h7xx_eval/hdf_config/hdf.hcb
```

**H3.3 ★ 两段式（本课最有价值的一条配置规则）**

- 事实（源码）：`drivers/hdf_core/framework/core/host/src/hdf_device_node.c:287`
  ```c
  devNode->deviceObject.property = HcsGetNodeByMatchAttr(HdfGetHcsRootNode(), deviceInfo->deviceMatchAttr);
  ```
  → **`device->property` 是按 `deviceMatchAttr` 去 hcs 树里反查的**，不是"读该 deviceNode 底下写的属性"。
- 所以正确写法是两段 + 一个 include：
  ```hcs
  /* 第一段：device_info/device_info.hcs —— 只说"用哪份配置" */
  i2c0 :: deviceNode {
      policy = 0;
      priority = 100;
      moduleName = "NSING_I2C_MODULE_HDF";
      serviceName = "";
      deviceMatchAttr = "n32h7xx_i2c";     /* ← 关键：不能留空 */
  }
  ```
  ```hcs
  /* 第二段：i2c/i2c_config.hcs —— 装值 */
  root {
      platform {
          i2c_config {
              match_attr = "n32h7xx_i2c";   /* ← 与上面的 deviceMatchAttr 同一个串 */
              port  = 1;
              speed = 100000;
          }
      }
  }
  ```
  ```hcs
  /* 第三件事：hdf.hcs 必须 include 它，否则节点根本没进树 */
  #include "device_info/device_info.hcs"
  #include "i2c/i2c_config.hcs"
  ```
- 失败表现：`deviceMatchAttr = ""` → `property == NULL` → 驱动走内置默认值 →
  **看起来"hcs 接好了"，其实一个值都没读到**（本工程实测日志：`no hcs node -> default port=1`）
- 与上游一致性：`device/soc/hisilicon/hi3518ev300/hdf_config/i2c/i2c_config.hcs` 就是同一范式（可对比讲）

**H3.4 控制器为什么需要两个节点**
- manager（`HDF_PLATFORM_I2C_MANAGER`，framework 自带）负责 `g_i2cManager` 与 `cntlrs[busId]` 数组；
- controller（我们的驱动）通过 `I2cCntlrAdd()` 把自己挂进数组。
- 缺 manager → `g_i2cManager == NULL` → `I2cCntlrAdd` 返回 `HDF_ERR_NOT_SUPPORT`（实测踩过）

### H4　驱动模型（6 min）▣

```c
struct HdfDriverEntry g_N32I2cDriverEntry = {
    .moduleVersion = 1,
    .moduleName    = "NSING_I2C_MODULE_HDF",   /* ← 与 hcs 的 moduleName 匹配 */
    .Bind          = N32I2cBind,
    .Init          = N32I2cInit,
    .Release       = N32I2cRelease,
};
HDF_INIT(g_N32I2cDriverEntry);                  /* ← 把入口指针放进 .hdf.driver 段 */
```

- 三个回调各自该做什么（**最容易写错的地方**）：

| 回调 | 该做 | 不该做 |
|---|---|---|
| `Bind` | 只做参数校验 | 不要在这里初始化硬件 |
| `Init` | 读 hcs、注册控制器/服务、取资源 | **不要调厂商 GPIO/外设初始化函数**（见 H8） |
| `Release` | 反向注销、释放 | — |

- 生命周期时序：`DeviceManagerStart()` → 逐节点 `Bind` → 逐节点 `Init`；失败则 `Release` 并析构
- 案例：**"Init 明明成功，设备却消失且无日志"**
  - 根因：`policy=2` 声明要发布 service，但 `deviceObject.service` 必须由 `PlatformDeviceCreateService()` 创建
    （`PlatformDeviceBind()` 只转发不创建）→ 发布被否决 → 节点析构；而 `devStatus` 在 Init 前已置 LAUNCHED，
    所以 hilog 也来不及说明白
  - 结论：**"看起来成功了"和"真的成功了"要分开验证**

### H5　注册与匹配：`.hdf.driver` 段（4 min）▣ 精读源码之一

- `HDF_INIT()` 把入口指针放进 `.hdf.driver` 段；`board.ld:104-109` 收拢：
  ```ld
  _hdf_drivers_start = .;
  KEEP(*(.hdf.driver))
  _hdf_drivers_end = .;
  ```
- **实测验证（建议现场 `nm` 一下，很有说服力）**：
  ```
  _hdf_drivers_start = 0x15025514
  _hdf_drivers_end   = 0x15025524      → 16 字节 = 4 个驱动入口
  ```
  正好对应 hcs 里的 4 个节点：GPIO / UART / I2C manager / I2C controller。
  → **"驱动有没有真被链进来"最硬的判据**（比 grep 源码可靠）

### H6　控制器 / 服务模型与虚表分发（5 min）▣ 精读源码之二

```c
/* 驱动侧：填一张 ops 表，把 cntlr 注册进框架 */
static struct I2cMethod g_n32I2cMethod = { .transfer = N32I2cTransfer };
g_n32I2cCntlr.ops   = &g_n32I2cMethod;
g_n32I2cCntlr.busId = 1;
I2cCntlrAdd(&g_n32I2cCntlr);          /* → manager->cntlrs[1] = cntlr  (i2c_core.c:56) */
```
```c
/* 框架侧：应用的一次 transfer 最终一定会落到某个驱动的函数指针 */
ret = cntlr->ops->transfer(cntlr, msgs, count);   /* i2c_core.c:227 */
```
- 三类对象的差异（讲清"服务"和"控制器"不是一回事）：

| 模型 | 代表 | 应用怎么拿到 | 例子 |
|---|---|---|---|
| Service | `HDF_PLATFORM_UART_0` | `UartOpen(0)` 按 service 名 | UART |
| Controller + busId | `I2cCntlr` | `I2cOpen(1)` 按 busId 查数组 | I2C |
| 直接设备 | — | — | 现在的 GPIO 实现 |

### H7　应用侧链路 + 怎么证明"真的走了 HDF"（3 min）▣

- 链路（每一跳都有行号，建议做成 PPT 一页）：
  ```
  app  I2cOpen(1) / I2cTransfer()
   → i2c_if.c:21,33        I2cCntlrGet / I2cCntlrTransfer
   → i2c_core.c:141        I2cCntlrGet → I2cManagerFindCntlr → manager->cntlrs[1]
   → i2c_core.c:227        cntlr->ops->transfer(...)   ← 虚表分发
   → i2c_n32h7xx.c:184     N32I2cTransfer → N32I2cOneMsg
   → n32_i2c_hw.c          N32I2cHwWrite/Read/Probe → SDK → CTRL2/STSINT
  ```
- **三层证据法**（教听众怎么自证，而不是听我说）：
  1. **头文件层**：`app_main.c` 只 `#include "i2c_if.h"`，没有任何 SDK 头
  2. **运行日志层**：`[I2C] driver Init() entered` 只存在于驱动 `Init()`，且紧跟 `DeviceManagerStart()`
  3. **机器码层**（最硬）：
     ```
     AppI2cEepromTask 的 bl/blx 目标：I2cOpen / I2cTransfer / I2cClose / osDelay / UartPuts ← 无任何 SDK 函数
     .data @0x24000160 (g_n32I2cMethod) = d9fc0015 = 0x1500fcd9 = N32I2cTransfer+1(Thumb)
     ```

### H8　HDF 常见失败模式（2 min）▣ 建议做成一张"排错卡"

| 现象 | 根因 | 查什么 |
|---|---|---|
| 驱动完全没启动，无日志 | `moduleName` 与 hcs 不一致 | `nm` 看 `.hdf.driver` 段里有没有它 |
| 驱动 Init 成功但设备消失 | `policy=2` 但 service 未创建 | 用 `PlatformDeviceCreateService()` |
| hcs 参数不生效 | `deviceMatchAttr` 留空 / 无对应 `match_attr` / `hdf.hcs` 没 include | 日志里的兜底提示 |
| `I2cCntlrAdd` 返回 `HDF_ERR_NOT_SUPPORT` | 缺 manager 节点，`g_i2cManager == NULL` | hcs 有没有 manager |
| 驱动 `Init()` 里访问外设就崩（`Type=11`） | 内核起来后调厂商 GPIO/外设函数越界 | 引脚配置搬到 `main()`、内核之前 |
| 驱动同时引 HDF 头与 SDK 头编译失败 | `enum IRQn` 重定义（两边都无保护宏） | 用 SoC 薄封装隔开 |
| 改了 hcs 却毫无变化 | `hb build` 不跟踪头依赖，或 hcb 没重新生成 | 删 `.o` 全量重编；看 `gen/.../hdf.hcb` 时间戳 |
